ANJANAM — secrets.txt
What must stay private, what this repo touches (names only), and how to rotate safely
================================================================================

IMPORTANT
---------
- Never paste real keys, passwords, or JSON into this file or into Git.
- If any secret was ever leaked (chat, screenshot, public repo), rotate it at the
  provider (Supabase, Razorpay, Google Cloud) immediately.

================================================================================
SECTION 1 — MUST NEVER BE EXPOSED TO USERS, STORE ADMINS, OR THE PUBLIC
================================================================================

These grant full data access, money movement, or account takeover. Keep them on
servers, in Supabase Edge Function secrets, or in CI secret stores only.

1.1 Database and Supabase privileged access
    - Postgres database password / full connection URI (non-pooled admin-style use)
    - Supabase service_role JWT (Dashboard: Project Settings → API)
      Used by Edge Functions in this repo; bypasses RLS — NEVER ship in Flutter/Web.

1.2 Payment provider (secret half of the pair)
    - Razorpay Key Secret (paired with Key Id)
    - Any Stripe/other gateway secret keys

1.3 OAuth / identity (where the provider issues a client secret)
    - OAuth client secrets (Google, Apple, etc.) — not in mobile/web clients

1.4 Email
    - SMTP password, SendGrid/Mailgun API keys used for transactional mail

1.5 Push / Google Cloud
    - FCM legacy server key (if still used anywhere)
    - Google Service Account JSON (full file) — contains private_key
    - This repo’s send-notification function uses base64 of that JSON as a secret

1.6 Webhooks and crypto
    - Webhook signing secrets
    - Any HMAC/API keys for third-party admin APIs
    - Field/file encryption keys

1.7 Operator / infrastructure
    - Personal access tokens (Supabase, GitHub, cloud consoles)
    - CI/CD secret values
    - Supabase JWT secret (self-hosted); on hosted Supabase you do not embed it in apps

================================================================================
SECTION 2 — OK IN THE CLIENT (WITH CORRECT DESIGN)
================================================================================

2.1 Supabase
    - Project URL (SUPABASE_URL) — public; real protection is RLS + policies
    - anon (publishable) key (SUPABASE_ANON_KEY) — designed for browsers/apps;
      must assume it is visible; never rely on “hiding” it

2.2 Razorpay
    - Key Id only (rzp_test_… / rzp_live_…) — used in app to open checkout
    - Payment verification must use Key Secret on the server (Edge Functions here)

2.3 Non-secret configuration
    - Auth redirect URLs, Site URL (Supabase Dashboard) — not passwords; still
      configure carefully to avoid open redirects

================================================================================
SECTION 3 — WHO MAY SEE WHAT
================================================================================

End users
    - Only their own session after login. No service_role, DB password, or
      payment/FCM secrets.

Store admins (in-app admin role)
    - Admin features via RLS-safe APIs or Edge Functions — not master keys.
    - Do not give them Dashboard access unless they are trusted operators.

Developers / DevOps
    - Need secrets to deploy and debug; store in password manager + CI secrets,
      not in source control.

================================================================================

These appear in code, docs, or commands for this project. Rotate at the provider
if compromised. Do not commit values.

4.1 Flutter build-time (dart-define / environment)
    SUPABASE_URL
    SUPABASE_ANON_KEY
    SUPABASE_FUNCTIONS_BASE_URL          (optional; functions base URL)
    RAZORPAY_KEY_ID                      (publishable Key Id in client)

    RAZORPAY_KEY_ID                      (must match test/live mode with secret)

Functions in this repo that expect the above (by name in code):

4.3 Firebase (mobile)

4.4 Files that sometimes hold secrets (must stay out of Git or use placeholders)
    - Local shell history, cmd.txt, temp notes, screenshots
    - .env files (if you add them) — add .env to .gitignore

================================================================================
SECTION 6 — STEPS TO USE NEW KEYS AND KEEP THEM HIDDEN
================================================================================

6.1 Generate or obtain new credentials
    - Supabase: Project Settings → API (new anon + service_role if project new)
    - Razorpay: Dashboard → generate new keys for test or live; retire old pair
    - Google Cloud: create new service account key only if needed; delete old key
      after migration

6.2 Store values only in secure locations
    - Password manager (1Password, Bitwarden, etc.) for human-readable backup
    - GitHub Actions / CI “Secrets” for builds
    - Supabase Dashboard → Edge Functions → Secrets for function runtime

6.3 Set Supabase Edge Function secrets (example pattern; run from machine with CLI)
    npx supabase@latest secrets set KEY_NAME="value"
    Repeat for each name in section 4.2. Never echo secrets into logs.

6.4 Point Flutter builds at new client-safe values
    - Use CI or local script with environment variables, not committed files:
      flutter build apk --dart-define=SUPABASE_URL=... --dart-define=SUPABASE_ANON_KEY=...
      (plus RAZORPAY_KEY_ID, etc.)
    - Production pipelines: inject from CI secrets, not from developer laptops only

6.5 Revoke old credentials
    - After new keys work in staging/production, disable/delete old Razorpay keys,
      old service account keys, and rotate Supabase JWT only by creating a new
      project or following Supabase docs if they offer rotation

6.6 Verify
    - Sign up / login, checkout (test mode), one Edge Function call, one push path
    - Confirm no secret appears in: APK strings dump, web bundle source map in
      public hosting, or public Git history (use git-secrets / scanning if needed)

6.7 Team discipline
    - No secrets in Slack/Email; use secret-sharing tools
    - Read-only Dashboard roles for non-operators
    - Separate Supabase projects for dev/staging/prod when possible
